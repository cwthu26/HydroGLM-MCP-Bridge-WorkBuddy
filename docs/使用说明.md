# 使用说明

本说明面向能运行本地 stdio MCP 服务的 AI 客户端。DeepSeek Harness、WorkBuddy、Claude Desktop 和 Codex 使用同一份 `server.py`，区别在于客户端配置入口和配置格式。

首次接触 MCP 可先阅读 [MCP 原理与调用场景](MCP原理与调用场景.md)，了解它解决什么问题、由谁决定调用，以及专业咨询与本地执行如何衔接。

## 1. 准备运行环境

安装 Python 3.10 或更高版本。检查命令：Linux/macOS 使用 `python3 --version`，Windows 使用 `py -3 --version`。MCP 服务只使用标准库，无需安装 OpenAI SDK、Node.js 或其他 pip 包。

将下载的文件夹解压到长期保留的位置，例如 Linux/macOS 的个人项目目录或 Windows 的 `D:\Tools\HydroGLM-MCP-Bridge`。后面生成的配置使用绝对路径，移动目录后需要重新生成。

以下命令都在项目目录运行。Windows 将 `python3` 替换成 `py -3`；若 Windows 没有 `py` 命令，使用实际 `python.exe` 路径。

## 2. 设置密钥

```bash
python3 configure_key.py --agent HydroGLM
```

输入绑定 HydroGLM 智能体的瀚海 API Key，终端不会回显。使用 HydroGLM-plus 时运行：

```bash
python3 configure_key.py --agent HydroGLM-plus
```

工具默认 `agent` 是 `HydroGLM`；仅配置 plus 密钥时，调用工具也必须指定 `agent="HydroGLM-plus"`。

每个模型只需保存一次，后续问答自动读取；保存 plus 密钥不会覆盖普通版密钥。需要更换时，重新运行对应命令。

保存位置为 `~/.config/hydroglm-mcp/credentials.json`；设置了 `XDG_CONFIG_HOME` 时使用该目录。这个位置与旧版一致。同一操作系统账户下通常可直接复用旧凭据；不同用户、容器或远程运行环境需要单独配置。

也可以在客户端启动 MCP 子进程时设置 `HANHAI_HYDROGLM_API_KEY` 或 `HANHAI_HYDROGLM_PLUS_API_KEY`。环境变量优先于凭据文件。GUI 客户端不一定继承终端临时环境变量，初次使用优先采用隐藏输入保存方式。

## 3. 生成客户端配置

根据客户端选择一条：

```bash
python3 generate_config.py --client workbuddy --output local.workbuddy.mcp.json
python3 generate_config.py --client claude --output local.claude.mcp.json
python3 generate_config.py --client codex --output local.codex.mcp.toml
python3 generate_config.py --client generic --output local.generic.mcp.json
```

生成器只创建片段文件，不写客户端设置。已有同名输出文件时会停止；确认需要覆盖后才使用 `--force`。如需指定另一 Python，增加 `--python` 并填写其可执行文件绝对路径。

默认配置名为 `hydroglm_bridge`。配置应在 MCP 实际运行的设备上生成；不能把 Linux 生成的解释器和脚本路径直接粘到 Windows。

## 4. 合并配置并加载

- [DeepSeek Harness 一键安装](DeepSeek-Harness.md)
- [WorkBuddy 配置示例](../examples/workbuddy.mcp.json)
- [Claude Desktop](Claude-Desktop.md)
- [Codex](Codex.md)

JSON 客户端把 `mcpServers.hydroglm_bridge` 合并进已有 `mcpServers`，TOML 客户端合并新的服务器表。保留其他 MCP 的配置。保存后使用客户端的重载功能或重启客户端。

需要填写的核心字段是 `command`（Python 可执行文件）和 `args`（`-X`、`utf8`、`server.py` 绝对路径）。选择本地 `stdio` 传输。服务由客户端启动；在终端单独运行 `server.py` 会等待标准输入，并不表示卡死。

## 5. 日常使用：直接提问，自动选用

接入完成后，像平常一样直接提问，无需输入服务器名或工具名：

> 水库汛限水位有什么作用？

涉及专业咨询与本地计算的任务：

> 解释 Muskingum 河道汇流模型及其适用条件，再用 Python 计算一个示例并验证水量平衡。

宿主 AI 按任务需求自动选用 HydroGLM 做专业咨询，随后用自己的工具完成 Python 执行、文件处理或绘图。工具描述已包含自动选用提示；可将 [按任务选用建议](按任务选用建议.md) 加入客户端自定义指令，使规则更明确。实际是否发起调用，以工具记录为准。

### 什么情况下适合调用

需要专业机理解释、模型参数说明、方法比较、调度规则或方案分析时，可考虑咨询。已有数据的直接绘图、普通编程和文档排版，通常由宿主直接处理。安装服务只让工具可用，不会强制每条消息调用。

### 使用 HydroGLM-plus

需要指定 plus 时，可以直接用自然语言说明：

> 这次使用 HydroGLM-plus，解释梯级水库联合调度需要考虑哪些约束。

宿主将模型选择转成工具参数 `agent="HydroGLM-plus"`；用户无需手写 JSON 或工具调用命令。

如果上次回答附带 `session_id`，追问时可显式传入该编号。桥接器不把 MCP 进程生命周期当作上游会话，也不会自动续接所有对话。

具体判断表、工作流示例及调用验证见 [MCP 原理与调用场景](MCP原理与调用场景.md)。

## 6. MCP 详细介绍

MCP 将外部专业能力作为工具接入当前 AI 工作流。本项目通过 `ask_hydroglm` 提供专业咨询：宿主 AI 自动判断相关需求、发出问题，桥接器读取密钥并请求 HydroGLM，再将回答交回宿主继续完成任务。

它解决的是“专业咨询如何与当前 AI 的本地工作衔接”的问题。例如，先分析调度规则，再由宿主读取数据、编写和执行程序，最后整理结果。日常使用只需说出任务，不必手动选择工具或反复输入密钥。

自动选用由宿主 AI 和客户端执行，受当前工具是否可用、任务内容和权限设置影响；桥接器本身不监听用户的全部消息。完整流程图、调用场景表和能力边界见 [MCP 原理与调用场景](MCP原理与调用场景.md)。

## 连接验证与排障

本节用于首次验证或未按预期调用时的排查，不是每次提问的操作步骤。

先确认客户端列出 `hydroglm_bridge` 下的 `ask_hydroglm`，直接问“水库汛限水位有什么作用？”，再查看是否产生真实工具调用记录。

如需单独检查工具能否正常返回，可以在排障时明确指定：

> 请调用 hydroglm_bridge 的 ask_hydroglm，只回复“连接正常”。

显式调用能帮助区分“工具连接或上游问答失败”与“宿主没有选用工具”；不能将这类排障命令当作日常使用前提。普通聊天中的“连接正常”字样也不能替代工具记录。

## 等待时间

本版 API 请求等待上限为 `server.py` 中的 `REQUEST_TIMEOUT_SECONDS = 600`。提前返回时立即结束。修改代码后，需要重新启动相应 MCP 子进程。

Codex 配置使用 `tool_timeout_sec = 660`。WorkBuddy 的 `timeout` 是官方文档定义的连接超时，单位为毫秒；本版样例省略该字段，使用客户端默认值。不同客户端对单次工具调用、取消和长请求的处理不同，不能保证每个客户端都会等待满 600 秒。客户端延长等待也不会改变上游网关自己的限制。参见 [WorkBuddy 官方字段说明](https://open.workbuddy.cn/docs/connector)、[Codex 官方配置说明](https://learn.chatgpt.com/docs/config-file/config-reference)。

## 排障

| 现象 | 检查方法 |
|---|---|
| 没有出现工具 | 检查客户端支持本地 stdio、JSON/TOML 语法及绝对路径，重新加载 MCP |
| Python 找不到 | 配置中使用实际解释器绝对路径；Windows 通过 `py -3` 运行生成器 |
| `No key is configured` | 在 MCP 使用的同一用户账户和运行环境配置对应智能体密钥 |
| HTTP 401 / 403 | 检查密钥有效性及其绑定智能体是否与 `agent` 一致 |
| HTTP 429 | 上游限流，稍后再试 |
| HTTP 5xx / 超时 | 检查网络与上游服务状态，记录时间及可用的 request-id |
| 模型列表 200，问答失败 | 模型列表与生成接口不同，继续检查真实问答接口 |
| 出现两个 `ask_hydroglm` | 旧、新 MCP 同时启用；按服务器名称区分或仅启用一个 |

只检查模型列表：

```bash
python3 diagnose.py --agent HydroGLM
```

真实问答探测（会发送问题并产生 API 请求）：

```bash
python3 probe_chat.py --agent HydroGLM --question '请只回复连接正常。'
```

现有服务将部分超时与系统连接错误合并为同一提示；不要仅凭该提示认定密钥错误或上游服务故障。
